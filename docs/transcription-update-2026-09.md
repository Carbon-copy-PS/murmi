# 逐字稿更新：2026 年 9 月

原本這套系統是做給瑞士市民大會用的，所以有特別針對德文、英文和法文調整。後來拿來處理台灣的中文討論，第二次轉錄卻還留著這些語言提示，而且會把第一次的結果蓋掉。

我們也發現，第二次轉錄使用的音訊可能混進下一段發言。這表示，即使第一次已經辨識得不錯，第二次也可能把內容改錯。不過，因為沒有保留當時的原始音訊和第一輪結果，我們不能確定某一段錯誤文字究竟是怎麼產生的。

這次先把第二次覆蓋的步驟拿掉，直接保留即時轉錄的完成結果。像「不要」「同意」這種短句也會留下來；按停止錄音時，系統會等最後一句轉完，若等不到，就提醒使用者可能有缺漏。存檔失敗會自動重試，某一段還沒收到，也不會一直卡住後面的文字；結果稍後抵達時，再補回原來的位置。

中文有時會被寫成簡體，所以我們另外加了文字轉換。選繁體中文時，字幕、逐字稿畫面和文字下載會顯示繁體；模型原本輸出的文字不會被改掉，可以切換查看，也可以下載原始資料。

## 為什麼先不換模型？

我們使用 [Nexdata 公開提供的台灣華語樣本](https://github.com/Nexdata-AI/98-Hours-Taiwan-Mandarin-Speech-Data-by-Mobile-Phone_Reading)做了實際 API 測試：十段真人錄音，共約 40.5 秒，參考文字共 106 個字元。三種設定各跑一次，合計 30 次轉錄。

| 設定 | 第一段字幕出現時間的中位數 | 排除簡繁體差異後的字元錯誤率 |
| --- | --- | --- |
| 原本的 `gpt-4o-transcribe` 設定 | 4.14 秒 | 0.94%（1/106） |
| `gpt-4o-transcribe`，改用中性的轉錄提示 | 4.15 秒 | 0.94%（1/106） |
| `gpt-live-transcribe`，低延遲設定 | 1.69 秒 | 0.94%（1/106） |

三組都有同一處「拉／啦」的差異。這是和資料提供者參考文字的字元比對結果，不代表一定聽錯了意思。新模型比較快，但這個小測試沒有顯示它比較準，因此目前保留 `gpt-4o-transcribe`。

這些是安靜環境下朗讀的句子，不是多人同時說話的討論現場；參考文字由資料提供者提供，未另外逐段人工校對。延遲從音訊開始播放計算，不含連線建立和瀏覽器顯示時間。新模型的測試在每段音檔結尾手動提交音訊；實際 API 拒絕了原有的伺服器語音活動偵測設定，不能只換模型名稱就直接套用。

## 保留原話，也保留核對的方式

- 原始逐字稿和每個完成轉錄項目的文字保持不變；繁體轉換只用於顯示和文字下載。
- 轉換採用 OpenCC `s2tw`（`opencc-js` 1.4.2），使用台灣正體字，不啟用額外的台灣慣用詞替換。
- 即時字幕每次轉換的是目前累積的整段文字，讓跨越兩次字幕更新的詞也能一起判斷。
- 「顯示原始文字」可以核對轉換前的內容；`.txt` 是可閱讀的逐字稿，`.json` 保留原始文字與現有的轉錄項目資料。
- 找不到的片段會標示為缺漏，不會自行補寫；尚未確認的即時字幕不會放進完成逐字稿下載。

轉換簡繁體不能修正聽錯的詞，也不能讓不相關的德文變回原本的中文。較早的場次若未保留第一輪結果或音訊，這次更新也無法補回那些資料。

## 驗證與已知限制

這批程式已於 2026 年 9 月 16–17 日分批部署到 [murmi.org](https://murmi.org)。部署前後有做資料比對，既有的討論、投票和公開結果沒有被改寫。

測試分開處理：實際音檔透過 API 測試辨識結果；自動化測試刻意模擬延遲、缺漏、重複結果和儲存失敗，檢查程式是否保留文字。PostgreSQL 測試也確認了重試不會重複存入同一段文字，重新載入後仍能取得最新內容。這些流程測試不代表模型已經更會辨識現場對話。

儲存重試佇列仍放在記憶體裡。如果資料庫故障期間伺服器也當掉，尚未存好的文字仍可能遺失。斷線期間未送達的音訊也不會自動補送。接下來仍需要用真實多人討論錄音，驗證噪音、插話和重疊發言的表現。

詳細實作與測試方式見 [轉錄工具說明](../backend/tools/README.md)。音訊、個別場次資料和完整測試輸出不收進這份來源程式庫。
